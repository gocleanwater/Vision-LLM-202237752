# 데이터 계약 — v0.1

상태: 1차 구현. 실제 모델 응답 검증 전. 아래 JSON은 형식 예시이며 실제 가족의 식사·실제 카메라 관측이 아니다. 키는 영어, 사용자 출력은 한국어로 한다.

## 1. 공통 규칙

- 한 번에 질문 하나만 순서대로 처리한다. 질문마다 폴더나 관리 번호를 만들지 않는다.
- 사진은 `runtime/camera.jpg`, 질문 음성은 `runtime/input.wav`, 답변 음성은 `runtime/response.wav`를 사용한다. 다음 질문 때 같은 파일을 덮어쓰며 이전 파일을 따로 보관하지 않는다.
- JSON 결과는 UTF-8로 저장한다. 필요한 경우 `runtime/detections.json`처럼 고정된 파일을 덮어쓴다.
- 촬영·녹음·분석이 성공한 뒤에만 다음 단계로 넘어간다. 실패했을 때 남아 있는 이전 사진이나 음성·추천 결과를 이번 결과로 사용하지 않는다.
- 함수의 실패는 예외로 전달하고 메인 프로그램이 단계에 맞는 한국어 오류 안내를 만든다. 별도 오류 JSON이나 상태 파일을 만들지 않는다. 실패를 빈 성공 목록으로 바꾸지 않는다. VLM 확인만 실패하면 애매한 후보를 제외한다.

## 2. YOLO 관측

```json
{
  "image_width": 1280,
  "image_height": 720,
  "detections": [
    {"detection_id": "d1", "class_id": 9, "ingredient_id": "egg", "confidence": 0.86, "bbox_xyxy": [100, 120, 260, 290]}
  ]
}
```

YOLO 예시는 관측 설명용 묶음이다. 코드에서는 이미지 크기와 `detections` 항목을 함수 인수로 전달하며 JSON 파일로 저장하지 않는다. 상자는 원본 사진 기준 픽셀 `x1,y1,x2,y2`이며 좌표는 영상 범위 안에 있고 너비·높이는 양수여야 한다. 신뢰도는 유한한 0~1 값이다. 클래스 번호는 사용 중인 모델의 `names`와 대조한다. 예시의 9번은 현재 데이터 YAML의 `egg`이며 다른 모델에도 9번이 계란이라고 가정하지 않는다.

## 3. 애매한 후보의 VLM 확인

YOLO 결과 중 `DETECT_CONF <= confidence < ACCEPT_CONF`인 후보만 전달한다. 후보 영역을 잘라 번호와 함께 하나의 이미지로 모으며, 번호는 YOLO의 `detection_id`와 대응한다. 아래 예시는 애매한 후보 `d1`, `d2`를 확인한 응답이다.

```json
{
  "checks": [
    {"detection_id": "d1", "ingredient_id": "egg"},
    {"detection_id": "d2", "ingredient_id": null}
  ]
}
```

- `checks`에는 전달한 후보만 각각 한 번씩 있어야 한다. 없는 후보 번호나 중복 번호가 있으면 잘못된 응답으로 처리한다.
- `ingredient_id`는 지원 재료 ID 또는 `null`이다. `null`은 확인하지 못했다는 뜻이며 해당 후보를 제외한다. 원래 YOLO 분류와 다르면 지원 재료 안에서 정정할 수 있다.
- `ACCEPT_CONF` 이상인 재료는 이 JSON과 별도로 그대로 유지한다. VLM 응답이 잘못됐거나 호출에 실패하면 애매한 후보만 제외한다.
- 최종 재료 목록은 확실한 YOLO 재료와 확인된 후보를 합쳐 중복을 제거한다. 최종 목록이 비면 재료 인식 불가로 처리한다.
- 애매한 후보가 없으면 VLM을 호출하지 않는다. 입력에 없던 후보나 YOLO가 놓친 재료를 추가하지 않는다.
- 두 기준값과 속도는 미확정이다. confidence는 모델 점수이며 정답 확률로 보장하지 않는다.
- 이 구조가 실제 인식 정확도를 보장하지는 않는다. 사진과 정답을 함께 보고 평가해야 한다.

## 4. 최근 식사 파일

파일은 Project02 루트의 `recent_meals.json`으로 둔다. 아래는 예시이며 실제 기록 파일은 아직 만들지 않았다.

```json
{
  "meals": [
    {"dish_name": "계란말이", "selected_on": "2026-11-06"},
    {"dish_name": "김치볶음밥", "selected_on": "2026-11-07"}
  ]
}
```

- `meals`는 사용자가 **먹기로 선택한 메뉴**의 목록이다. 실제 섭취를 확인한 기록이 아니다.
- `selected_on`은 한국 시간 기준 선택 날짜(`YYYY-MM-DD`)다. 이는 3일을 구분하기 위한 날짜이며, 상세한 시각이나 처리 시간은 저장하지 않는다.
- 오늘이 `D`라면 `D-2 <= selected_on <= D`인 기록을 모두 제외 목록에 넣는다. 예를 들어 오늘이 11월 7일이면 5·6·7일이며, 4일 이전은 제외한다. 과거 72시간을 뜻하지 않는다.
- 개수 제한은 없다. 3일 안에 9개를 선택했다면 9개 모두 사용한다. 고정 길이 deque 대신 날짜로 목록을 거른다.
- 메뉴 생성 직전에 날짜를 확인해 파일을 읽고, 보완 추천에도 같은 목록을 사용한다. 오래된 항목이 파일에 남아 있어도 추천 제외 대상에는 넣지 않는다.
- 처음 실행해 파일이 없으면 `{"meals": []}`로 초기화한다. 기존 파일의 JSON·날짜·메뉴가 손상됐으면 오류를 알리고 빈 기록으로 덮어쓰지 않는다.
- 사용자가 메뉴명을 명확히 말하고 먹기로 정하면 정규화한 메뉴명과 선택 날짜를 추가한다. 추천한 메뉴인지, 추천을 먼저 받았는지, 최근 기록에 이미 있는지는 저장의 제한 조건이 아니다. 등록된 별칭은 대표 이름으로 정리한다.
- 저장할 때 3일 밖의 오래된 기록을 정리하고 새 선택을 추가한다. 임시 파일에 정상적으로 쓴 뒤 기존 파일을 교체해, 저장 실패 시 기존 기록을 보존한다. 질문별 보관 폴더나 로그를 만드는 것은 아니다.
- 음성 입력 한 번은 한 번만 처리해 저장한다. 재시작하거나 새 추천을 받아도 사용자가 메뉴 이름을 직접 말해 기록할 수 있다. 이전 추천 목록을 선택 허용 목록으로 관리하지 않는다.
- `둘 다 먹자`는 현재 이벤트에서 마지막으로 안내한 메뉴 전부를 기록한다. 마지막 안내가 1개면 그 메뉴만 기록한다. 여러 메뉴에는 같은 선택 날짜를 붙이고 한 번에 파일에 저장한다. 일부만 저장한 상태를 성공으로 처리하지 않는다.
- 현재 추천 이벤트에서 마지막으로 안내한 1~2개 메뉴와, 그동안 안내한 모든 메뉴 이름을 메모리에만 둔다. 마지막 목록은 선택 문맥, 전체 목록은 `딴 메뉴 없어?`의 중복 제외에 사용한다. 이벤트가 끝나면 둘 다 비운다. 추천 밖 메뉴의 직접 선택은 계속 허용한다.
- 메뉴명이 없는 `좋아`, 참조할 추천이 없는 `둘 다 먹자`, 부정·의문 표현인 `안 먹자`, `먹을까?`처럼 선택이 불명확하면 저장하지 않고 `그래서 뭘 드시나요? 알려주세요!`라고 묻는다. 추천 밖 메뉴라도 이름과 긍정 선택이 명확하면 저장한다. 새 추천 질문이면 촬영·추천으로 들어간다.
- `그걸 먹자`, `아무 음식 먹자`처럼 메뉴명이 특정되지 않은 표현도 저장하지 않고 정해진 문장으로 되묻는다. 기존 추천 문맥은 유지한다. 정규식과 등록한 표현을 검사하는 방식이므로 모든 자연어의 모호함을 완전히 판별하지는 못한다.
- 추천·TTS 출력만으로는 메뉴를 추가하지 않는다. 메뉴 선택 때 촬영·YOLO·VLM을 다시 실행하거나 재료 재고를 차감하지 않는다.

## 5. 이름 정규화

사용자 선호에 따라 표시·음성·새 저장에서는 `달걀 → 계란`, `달걀말이 → 계란말이`, `달걀볶음밥 → 계란볶음밥`으로 정리한다. 기존 기록을 강제로 다시 쓰지는 않으며, 읽을 때 같은 정규화를 적용해 제외·중복 판정을 유지한다. YOLO 클래스 ID `egg`는 바꾸지 않는다.

- 음식명: Unicode NFKC 정규화 → 앞뒤·내부 공백 정리 → 영문 대소문자 정리 → 등록된 음식 별칭을 대표 이름으로 변환한다.
- 초기 별칭 검증 예: `계란말이`와 `달걀말이`는 같은 대표 이름, `계란 볶음밥`과 `달걀볶음밥`도 같은 대표 이름으로 처리한다.
- 재료명: 모델의 영어 클래스명 → 고정 `ingredient_id` → 한국어 표시명으로 변환한다. 예: `egg → 계란`, 입력 별칭 `달걀 → egg`.
- 선택 문장의 음식명은 기존 추천 이름과 먼저 대조하고, 모르는 이름 끝의 `로`는 임의로 잘라내지 않는다. 일부 조사는 한글 받침·공백을 검사해 제거하지만 모든 형태소를 해석하지는 못한다.
- 음식 별칭과 재료 별칭을 분리한다. 재료 단어 치환만으로 모든 음식명을 같다고 판단하지 않는다.
- 최근 식사와 추천, 추천 항목끼리 비교할 때 같은 음식 정규화 함수를 사용한다.
- 새 이벤트에서는 이전 이벤트의 단순 추천 목록을 제외 집합에 넣지 않는다. 같은 이벤트의 대안 요청에는 이미 안내한 메뉴 이름을 정규화해 임시 제외한다.
- 미등록 동의어·지역별 음식명은 완전하게 검증할 수 없다. 발견한 경우 별칭과 재현 사례를 추가하고 한계로 기록한다.

## 6. Gemma 메뉴 응답과 최종 출력

Gemma는 보유 재료를 조합해 메뉴를 자유롭게 제안한다. 추가 재료를 준비해야 하는 메뉴도 허용한다. 아래 예시는 관측한 재료가 감자·당근·양파일 때의 형식이며 완전한 레시피가 아니다.

```json
{
  "menus": [
    {
      "dish_name": "카레",
      "available_ingredients": ["potato", "carrot", "onion"],
      "additional_ingredients": ["카레가루"]
    },
    {
      "dish_name": "채소잡채",
      "available_ingredients": ["carrot", "onion"],
      "additional_ingredients": ["당면", "간장"]
    }
  ]
}
```

- `menus`는 최대 2개다. 항목에는 `dish_name`, `available_ingredients`, `additional_ingredients`를 넣는다. 조리 방법이나 선정 이유는 프롬프트에서 요구하지 않는다.
- 메뉴명의 줄바꿈·앞뒤 공백을 정리하고 비어 있는지 검사한다. 문장부호가 있다는 이유만으로 일괄 거절하지 않는다. 최근 메뉴와 두 추천 사이의 중복은 정규화한 이름으로 검사한다.
- `available_ingredients`는 해당 메뉴에 활용할 보유 재료 ID다. 한 종류 이상이어야 하며, 관측 재료와 명시적 상시 재료 안에 모두 있어야 한다. 여러 재료를 조합해도 된다.
- `additional_ingredients`는 추가로 준비할 재료의 한국어 이름 목록이다. 필요 없으면 `[]`다. 카레가루·당면처럼 YOLO 지원 클래스 밖의 재료도 허용하지만 보유 재료나 탐지 결과로 간주하지 않는다.
- 이미 보유한 재료는 구매 목록에 중복해서 넣지 않는다. 알려진 한영 이름·별칭으로 비교하고, 모든 재료의 동의어를 완전하게 판별한다고 주장하지 않는다.
- 소금·식용유·쌀 등도 자동 보유로 가정하지 않는다. 상시 보유 설정이 없고 필요하다고 제안한다면 추가 재료 목록에 넣는다. 구매 목록이 과도해지지 않도록 메뉴당 최대 2종을 초안으로 제안하며, 실제 상한은 아직 미확정이다.
- 추가 재료의 매장 재고·가격·구매 가능 여부를 확인하는 기능은 없다. 이름만 안내하고 확인하지 않은 정보를 말하지 않는다.
- 유효 항목이 1~2개면 그대로 안내한다. 1개를 2개로 채우기 위한 보완 호출은 하지 않는다. 올바른 빈 목록이면 `추천할 메뉴가 없어요`라고 답한다. 잘못된 형식이나 금지 메뉴만 반환한 응답은 최대 1회 수정 요청하고, 유효한 후보가 없으면 추천 불가 또는 형식 오류를 구분한다.
- 메뉴가 1개면 `추천 메뉴는 {A}입니다.`, 서로 다른 메뉴가 2개면 `추천 메뉴는 {A}, {B}입니다.`로 시작한다. 추가 재료가 있는 메뉴에만 `{메뉴}의 추가 재료는 {재료 목록}입니다.`를 짧게 덧붙인다. 내부 JSON은 그대로 읽지 않는다.
- 사용자가 메뉴를 선택하면 메뉴명과 선택 날짜만 식사 파일에 저장한다. 구매 완료·실제 섭취·재료 수량 변화를 자동으로 기록하지 않는다.

이 목록은 Gemma의 제안이다. 실제 요리에 필요한 모든 재료가 빠짐없이 적혔는지 코드만으로 완전 검증하지 못한다. 사진·보유 재료·추가 재료와 메뉴를 함께 보고 타당성을 확인한다.

## 7. 파일 보관

질문별 사진·음성·분석 이력과 상세 로그를 모아 저장하는 기능은 만들지 않는다. 동작 확인에 필요한 내용은 터미널에서 확인한다. `recent_meals.json`은 다음 추천에도 사용하므로 유지하고, 사용자의 명확한 메뉴 선택 때만 갱신한다. 테스트에서는 가상 식사 파일을 사용한다.

## 8. 식재료 종류 조회

- `냉장고에 뭐 있어?` 같은 질문은 현재 사진을 새로 촬영해 YOLO로 탐지하고, 애매한 후보만 기존 VLM 확인 규칙을 적용한다. 계속 추적하거나 이전 사진을 그대로 쓰는 기능은 아니다.
- 최종 재료 ID를 중복 없이 모아 한국어 이름으로 표시한다. 예를 들어 `egg, egg, potato, carrot`은 `계란, 감자, 당근`으로 안내한다. 숫자·수량 필드는 응답에 넣지 않는다.
- 응답 형식은 `현재 보이는 식재료는 {재료 종류 목록}입니다.`이다. 카메라에서 확인한 목록이지 가려진 곳까지 포함한 전체 재고라고 주장하지 않는다.
- 확인된 재료가 없으면 기존 재료 인식 불가 안내를 사용한다. 냉장고가 비었다고 단정하지 않는다.
- 메뉴 생성·추가 구매 제안·식사 기록 읽기와 갱신은 하지 않는다. 기존 최근 추천 문맥은 유지한다.

## 9. 추천 이벤트 안의 임시 메뉴 목록

- 현재 이벤트에서 실제로 안내한 메뉴 이름 전체와 마지막 안내 목록(1~2개)을 메모리에만 유지한다. 생성했지만 거절한 후보는 안내 목록에 넣지 않는다.
- `딴 메뉴 없어?`에는 이미 안내한 이름도 정규화해 제외한다. 다시 대안을 요청해도 앞선 메뉴로 되돌아가지 않게 전체 안내 목록을 사용한다.
- 유효한 대안 1개도 성공이다. 후보가 없으면 `추천할 메뉴가 없어요`라고 말한다. 후보 없음 안내는 모델이 유효한 대안을 내놓지 못했다는 뜻이며 전수 탐색 결과는 아니다.
- 선택 저장 성공·종료·취소·후보 없음·새 일반 추천 시작·프로그램 종료 시 임시 목록을 비운다. 파일에는 사용자가 먹기로 선택한 메뉴와 날짜만 저장한다.
- 되묻기나 저장 실패 중에는 문맥을 유지하고, 새 이벤트에서는 지난 단순 추천 이력을 제외 조건으로 가져오지 않는다.

## 10. 연속 음성 입력

- 대기 중 마이크에서 음성 시작·끝을 감지해 한 발화만 `runtime/input.wav`에 저장하고 STT로 전달한다. 다음 발화 때 같은 파일을 덮어쓴다.
- 짧은 입력 버퍼는 발화 처리용 메모리이며 녹음 이력을 파일로 쌓지 않는다. 세부 감지 도구·무음 길이·최대 발화 길이는 미확정이다.
- 처리·TTS 중 음성은 새 작업으로 실행하거나 나중에 처리할 목록으로 저장하지 않는다. 끝나면 남은 입력을 버리고 자동으로 연속 감지를 재개한다.
- 빈 인식 결과는 무시한다. 실제 잡음·말소리·스피커 잔향 구분은 장치에서 검증한다.

## 11. 지정 메뉴의 전체 필요 재료와 차집합

Gemma의 텍스트 응답은 아래 형식을 따른다. 음식과 재료는 형식 예시다.

```json
{
  "dish_name": "카레",
  "ingredients": ["감자", "당근", "양파", "카레가루"]
}
```

- 키는 `dish_name`, `ingredients`만 허용한다. 메뉴명은 요청한 표기를 복사하고 정규화 후 같은지 검사한다. 다른 음식의 응답은 거절한다.
- `ingredients`는 추가 구매 목록이 아니라 **전체 필요 재료**의 비어 있지 않은 문자열 목록이다. 빈 목록을 모든 재료 보유로 해석하지 않는다. 수량·조리법·설명은 요청하지 않는다.
- 코드가 `전체 필요 재료 - 새로 관측한 재료`를 계산한다. 영어 ID와 등록된 한국어 이름·별칭을 비교하고 같은 재료는 한 번만 안내한다. 지원 클래스 밖 재료명도 허용한다.
- 결과가 있으면 `지금 사와야 하는 재료는 {목록}입니다.`, 없으면 `지금 사와야 하는 재료는 없어요.`로 만든다. 후자는 Gemma의 제안 목록을 기준으로 한 결과이지 실제 요리의 모든 필수 재료 검증은 아니다.
- 잘못된 형식·다른 메뉴·빈 필요 재료는 최대 1회 보완 후 실패를 알린다. 관측 실패는 구매 목록으로 바꾸지 않는다.
- 식사 기록 파일과 추천 이벤트 상태는 바꾸지 않는다. 이 응답을 새 탐지 결과나 확정 식사로 저장하지 않는다.
