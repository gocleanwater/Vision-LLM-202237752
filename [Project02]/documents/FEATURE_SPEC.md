# 기능명세 — v0.1

작성일: 2026-11-07. 상태: **1차 코드 구현 / 로컬 규칙 검증 완료, 실제 장치 검증 전**.

## 1. 개발 동기와 시연 가정

매일 가족의 식사를 준비하며 메뉴를 고민하시는 어머니의 부담을 줄이고자 한다. 보유 재료와 최근 식사 결정 기록을 바탕으로 음성으로 메뉴를 물어보면 최근에 먹기로 선택한 음식과 겹치지 않는 메뉴를 제안한다.

- 책상에 펼친 식재료를 냉장고 안의 식재료라고 가정한다.
- 사용자가 추천 메뉴를 먹기로 선택하면 이 프로그램이 직접 식사 기록 파일을 갱신한다. 별도 기록 장치를 가정하지 않는다. 이 기록은 실제 섭취를 확인한 것이 아니라 식사 메뉴를 결정한 기록이다.
- 실제 냉장고 재고의 완전한 파악, 자동 식사 인식, 사업성 검증은 이번 범위가 아니다.

## 2. 확정된 요구사항

| ID | 기능 | 완료 시 확인할 동작 |
| --- | --- | --- |
| FR-01 | 연속 음성 감지 입력 | 대기 중 마이크에서 음성 시작과 끝을 감지하고 완료된 한국어 발화를 STT로 전달한다. 키·버튼 입력은 필요 없다. 무음·빈 결과는 작업을 시작하지 않으며 응답 후 자동으로 다시 듣는다. |
| FR-02 | 질문 의도 구분 | 메뉴 질문은 촬영·추천, 재료 조회는 촬영·종류 안내, 먹기로 한 메뉴 선택은 기록 저장으로 나눈다. |
| FR-03 | 현재 재료 탐지 | 요청 이후 촬영한 사진에 식재료용 YOLO11n을 적용하고 이름·상자·신뢰도를 얻는다. |
| FR-04 | 애매한 후보만 VLM 확인 | confidence가 높은 재료는 바로 사용한다. 애매한 후보 영역은 하나의 이미지로 묶어 Gemma VLM에 한 번 전달한다. 그런 후보가 없으면 이미지 분석을 생략한다. |
| FR-05 | 즉시 추천 | 인식한 재료를 확인받는 질문 없이 추천으로 넘어간다. 불확실한 관측은 제외하거나 인식 실패로 처리한다. |
| FR-06 | 최근 3일 메뉴 제외 | 한국 시간 기준 오늘·어제·그저께에 먹기로 선택한 모든 메뉴를 파일에서 읽어 추천에서 제외한다. 개수 제한은 없으며 등록된 음식 별칭도 같은 메뉴로 비교한다. |
| FR-07 | 재료 조합·추가 구매 메뉴 생성 | Gemma가 보유 재료를 조합해 메뉴를 제안한다. 없는 재료를 조금 추가로 준비하는 메뉴도 허용하며 구매할 재료를 구분한다. 고정 메뉴 목록에서 선택하지 않는다. |
| FR-08 | 코드 검증·추천 간 중복 금지 | 구조·메뉴명·재료 ID를 검사하고, 한 번에 추천하는 최대 두 메뉴가 서로 다르며 최근 3일간 선택한 메뉴와도 겹치지 않을 때만 성공 출력한다. 음식 별칭도 같은 메뉴로 비교한다. |
| FR-09 | 메뉴·추가 재료 음성 출력 | 코드가 유효한 메뉴를 1~2개 안내하고, 필요한 경우 메뉴별 추가 구매 재료를 짧게 덧붙여 Piper로 재생한다. 레시피·선정 이유는 출력하지 않는다. |
| FR-10 | 메뉴 선택 시 기록 갱신 | 추천만 할 때는 메뉴 기록을 추가하지 않는다. 사용자가 메뉴명을 명확히 말하고 먹기로 정하면 추천 여부와 관계없이 메뉴와 선택 날짜를 저장한다. |
| FR-11 | 중복 요청 억제 | 처리 중에는 새 추천 작업을 중첩 실행하지 않고 사용자가 처리 중임을 알 수 있게 한다. |
| FR-12 | 선택 발화 처리 | `그래, 계란말이 먹자`처럼 메뉴명이 있는 긍정 선택은 정규화해 기록한다. 추천 밖 메뉴와 추천을 받기 전의 선택도 허용하며, 카메라·YOLO·VLM을 다시 실행하지 않는다. |
| FR-13 | 기록 유지·저장 실패 처리 | 재시작 후에도 저장한 메뉴를 날짜로 걸러 사용한다. 저장 실패 시 성공 안내를 하지 않고, 기존 기록을 보존한다. |
| FR-14 | 현재 식재료 종류 조회 | `냉장고에 뭐 있어?`, `식재료 뭐뭐 있어?`라고 물으면 새 사진을 분석해 재료 종류만 음성 안내한다. 중복 종류·개수·메뉴 추천·구매 제안은 제외하고 식사 기록도 읽거나 갱신하지 않는다. |
| FR-15 | 다른 메뉴와 이벤트 임시 목록 | `딴 메뉴 없어?`는 현재 추천 이벤트에서 이미 안내한 메뉴를 임시 제외해 최대 2개를 다시 제안한다. 1개도 안내하며 없으면 `추천할 메뉴가 없어요`라고 말한다. 임시 목록은 메모리에만 두고 이벤트 종료 때 삭제한다. |
| FR-16 | 지정 메뉴의 구매 재료 조회 | 원하는 요리를 말하며 살 재료를 물으면 현재 사진을 새로 분석하고, Gemma의 전체 필요 재료 제안에서 보유 종류를 코드로 제외해 안내한다. 식사 기록·추천 이벤트 문맥은 유지한다. |

## 3. 출력 형식

질문 의도에 맞는 재료 종류·메뉴명·추가 재료·기록 안내를 정해진 문장에 채운다. 내부 JSON이나 모델의 자유 문장을 그대로 읽지 않는다.

| 결과 | 사용자 출력 |
| --- | --- |
| 유효한 메뉴 1개 | `추천 메뉴는 카레입니다.` |
| 유효한 메뉴 2개 | `추천 메뉴는 계란말이, 감자볶음입니다.` |
| 추가 구매가 필요한 메뉴 | `추천 메뉴는 카레, 채소잡채입니다. 카레의 추가 재료는 카레가루입니다. 채소잡채의 추가 재료는 당면, 간장입니다.` |
| 지정 메뉴 구매 재료 조회 | `지금 사와야 하는 재료는 카레가루입니다.` |
| 구매할 재료가 남지 않음 | `지금 사와야 하는 재료는 없어요.` |
| 구매 재료 질문에 메뉴가 없음 | `어떤 메뉴의 재료를 살지 메뉴 이름을 말해 주세요.` |
| 식재료 종류 조회 | `현재 보이는 식재료는 계란, 감자, 당근입니다.` |
| 유효한 메뉴나 다른 추천 후보가 없음 | `추천할 메뉴가 없어요` |
| 재료 인식 불가 | `식재료를 확인하지 못했어요. 재료가 잘 보이도록 놓고 다시 질문해 주세요.` |
| 식사 기록 읽기 실패 | `최근 식사 기록을 읽지 못했어요. 기록 파일을 확인해 주세요.` |
| 메뉴 선택 저장 성공 | `계란말이로 기록했어요.` |
| 추천 두 메뉴를 모두 선택해 저장 성공 | `두 메뉴를 기록했어요.` |
| 메뉴 선택이 불명확함 | `그래서 뭘 드시나요? 알려주세요!` |
| 메뉴 선택 저장 실패 | `선택한 메뉴를 저장하지 못했어요. 다시 시도해 주세요.` |
| 모델 결과가 계속 유효하지 않음 | `메뉴 추천을 완료하지 못했어요. 다시 질문해 주세요.` |

위 음식명과 재료는 형식 예시이며 완전한 레시피나 실제 관측에 따른 검증 결과가 아니다. 최대 2개 메뉴와 필요한 추가 재료를 짧게 안내하는 것은 사용자 결정이며, 구체적인 안내 템플릿과 실패 문장은 구현 초안이다. 추가 재료가 없는 메뉴는 추가 안내를 생략한다. 유효한 메뉴가 1개면 그 메뉴만 추천한다.

선택 저장 후의 짧은 안내는 메뉴 두 개를 추천하는 응답과 구분한다. `둘 다 먹자`는 현재 이벤트에서 마지막으로 안내한 메뉴 모두를 같은 날짜로 저장한다. 마지막 안내가 1개면 1개만 저장한다. 참조할 추천이 없거나 `안 먹자`, `먹을까?`, `좋아`처럼 선택이 불명확하면 저장하지 않고 `그래서 뭘 드시나요? 알려주세요!`라고 묻는다. 추천이 없거나 추천에 없던 메뉴라도 이름과 먹기로 한 의사가 명확하면 저장한다. 최근 3일 기록과의 중복 금지는 AI 추천에만 적용하며, 사용자가 다시 먹기로 정하는 것을 막지 않는다.

## 4. 범위와 한계

- 한 요청에서 필요한 사진 한 장을 분석한다. 연속 영상 VLM 분석은 요구하지 않는다.
- YOLO의 탐지 하한 `DETECT_CONF` 이상, 바로 사용할 기준 `ACCEPT_CONF` 미만인 후보만 VLM에 보낸다. `ACCEPT_CONF` 이상은 바로 사용한다. 두 기준값은 실제 사진으로 정하며 `0 <= DETECT_CONF < ACCEPT_CONF <= 1`을 만족해야 한다. 탐지 하한 미만은 후보에 넣지 않는다.
- VLM의 확인 실패·타임아웃은 해당 후보를 제외하는 것으로 처리한다. YOLO에서 확실하게 탐지한 재료는 유지하고, 최종 재료가 모두 비었을 때만 재료 인식 불가로 안내한다.
- YOLO가 아예 놓친 재료를 추가로 찾는 기능은 두지 않는다. VLM도 틀릴 수 있으므로 확인 결과가 정답이라고 보장하지 않는다.
- YOLO는 식재료 전용 학습 모델을 사용한다. 기본 COCO 모델을 식재료 36종 모델이라고 설명하지 않는다.
- 현재 학습 클래스에 두부·김치·대파는 없다. 시연 재료는 학습 후 재료별 성능을 보고 결정한다.
- 보유 재료는 관측한 재료 ID와 명시적 상시 재료만 사용한다. 추가로 준비할 재료는 별도 목록으로 제안할 수 있으며 YOLO 클래스에 한정하지 않는다. 기본 양념을 자동 보유한다고 가정하지 않는다.
- 자유 생성 메뉴가 요리로 성립하는지, 필수 재료가 빠지지 않았는지 코드만으로 완전 검증할 수 없다. 알려진 이름·재료 규칙과 실제 시연으로 평가한다.
- 메뉴별 추가 재료 이름만 안내한다. 매장 검색·재고 확인·가격 비교·주문, 조리 단계, 영양 분석, 유통기한·신선도 판정은 범위 밖이다.
- 새 추천 이벤트에서는 이전 이벤트에서 추천만 했던 메뉴를 다시 추천할 수 있다. 같은 이벤트의 `딴 메뉴 없어?`에는 이미 안내한 메뉴들을 임시 제외한다. 이 목록은 파일에 저장하지 않고 이벤트 종료 때 비운다.
- 음성 입력은 연속 감지로 확정했다. 발화 종료를 판단하는 무음 길이·최대 발화 길이·감지 기준과 모델 제한 시간·탐지 임계값은 [남은 결정](OPEN_DECISIONS.md)에 따른다. 처리·TTS 중에는 새 발화를 실행하거나 쌓지 않는다. 측정 전 응답 속도를 보장하지 않는다.

## 5. 완료 기준

1. 하네스에서 정상·중복·최근 메뉴·실패 시나리오가 예상대로 동작한다.
2. Jetson에서 STT → 카메라 → YOLO → 필요한 경우만 Gemma VLM 확인 → Gemma 메뉴 추천 → TTS를 실제로 연결한다. 애매한 후보가 있는 경우와 없는 경우를 모두 확인한다.
3. 서로 다른 재료 배치와 최근 식사 파일로 연속 요청을 시연한다.
4. 메뉴 선택 후 기록 갱신, 날짜 경계, 재시작 후 기록 유지와 저장 실패를 검증한다. 질문별 사진·음성·상세 로그 자동 보관은 만들지 않으며, 모의 실행과 실제 실행을 구분한다.
5. 오인식·추천 실패·처리 지연을 기록한다. 실패 사례를 숨기거나 성공으로 바꾸지 않는다.

## 6. 지정 메뉴의 구매 재료 조회

`나 카레가 먹고 싶어. 지금 사와야 하는 재료가 뭐야?`는 추천·식사 선택과 구분해 처리한다. 메뉴명을 먼저 추출하고 현재 사진으로 YOLO·필요 시 VLM 확인을 수행한다. 메뉴가 없으면 관측 전에 되묻는다. `메뉴 추천해 줘. 추가 재료도 알려줘`는 기존 메뉴 추천이다.

Gemma는 해당 요리의 전체 필요 재료 이름을 제안하고 코드는 보유 종류를 제외한다. 등록된 한영 이름·별칭 비교와 중복 제거를 적용한다. 소금·식용유 등도 자동 보유로 가정하지 않는다. 관측이 비거나 실패하면 기존 재료를 재사용하거나 모든 재료를 구매 목록으로 만들지 않는다.

식사 파일은 읽거나 쓰지 않고, 진행 중인 추천 이벤트의 재료·마지막 메뉴·안내 집합도 유지한다. 요리가 먹고 싶다는 표현만으로 식사 결정을 저장하지 않는다. 요리법·수량·매장 정보는 제외한다. 전체 재료의 의미적 완전성은 모델에 의존하며, 등록되지 않은 이름·자연어 표현을 완전히 해석한다고 보장하지 않는다. 실제 Gemma와 장치 연동은 별도 검증한다.
