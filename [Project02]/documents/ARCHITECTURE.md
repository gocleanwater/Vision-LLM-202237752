# 구조 설계 — v0.1

상태: 구현 전. 기능 기준은 [기능명세](FEATURE_SPEC.md), JSON 기준은 [데이터 계약](DATA_CONTRACTS.md)이다.

## 1. 선택한 구성과 대안

| 결정 | 선택 | 이유와 대안의 차이 |
| --- | --- | --- |
| 추천 방식 | Gemma 자유 생성 + 코드 검증 | 사용자 결정. 고정 메뉴·필수 재료 목록에서 고르는 대안보다 유연하지만 요리의 성립 여부를 완전 검증할 수 없다. |
| 재료 확인 | 확인 질문 없이 바로 추천 | 사용자 결정. 확인·수정 대화를 두는 대안보다 짧지만 오인식이 추천에 이어질 수 있다. |
| VLM 이미지 분석 | confidence가 애매한 YOLO 후보만 한 번에 확인 | 사용자 결정. 매번 전체 사진을 분석하는 대안보다 불필요한 이미지 분석 호출을 줄이지만 YOLO 미검출 재료는 확인하지 못한다. |
| 모델 실행 | 환경별 별도 프로세스, 공통 요청 계약 | 초안 제안. 한 Python 환경에 모든 라이브러리를 합치는 방식보다 기존 Jetson 환경을 보존하기 쉽다. |

## 2. 역할 분담

- **메인 프로그램:** 음성 입력, 의도 판정, 순차 단계 실행과 타임아웃, 결과 검증, 고정 문장 생성.
- **Vision 어댑터:** 현재 사진 촬영과 YOLO 식재료 탐지. 탐지는 가중치의 클래스명으로 해석한다.
- **Gemma 어댑터:** 애매한 YOLO 후보를 모은 이미지의 VLM 확인, 이어서 재료·최근 식사에 대한 텍스트 메뉴 생성. 확인할 후보가 없으면 이미지 분석만 생략한다. 같은 프로세스에서 모델을 재사용하는 안을 우선 시험한다.
- **식사 기록 관리:** Project02 루트 `recent_meals.json`에서 한국 시간 기준 오늘·어제·그저께의 선택 메뉴를 읽는다. 사용자의 명확한 메뉴 선택 때 날짜와 메뉴를 저장한다. 개수 제한은 없다.
- **규칙 계층:** 재료·음식 이름 정규화, JSON 검사, 최근 메뉴와 중복 제거, 응답 문장 작성. 모델과 장치에 의존하지 않는다.
- **STT/TTS 어댑터:** 대기 중 연속 음성 감지, 발화 구간 녹음과 whisper.cpp 실행, Piper 환경의 Python 실행, 오디오 장치 입출력.

## 3. 한 요청의 흐름

`IDLE → RECORDING → TRANSCRIBING → INTENT_CHECK → CAPTURING → DETECTING → ANALYZING → READING_HISTORY → RECOMMENDING → VALIDATING → SPEAKING → IDLE`

- `ANALYZING`은 애매한 후보가 있을 때만 거친다. 메뉴 추천에서 그런 후보가 없으면 `DETECTING`에서 `READING_HISTORY`로 넘어간다.
- 재료 조회 질문은 촬영·탐지·필요한 VLM 확인 후 `SPEAKING → IDLE`로 간다. 식사 기록 읽기·메뉴 생성은 건너뛴다. 재료 ID의 중복을 제거하고 한국어 이름을 정해진 문장으로 만들어 TTS에 전달한다. 최근 추천 문맥은 덮어쓰지 않는다.
- 음성 의도가 메뉴명을 명확히 말한 긍정 선택이면 `INTENT_CHECK → SAVING_HISTORY → SPEAKING → IDLE`로 처리한다. 촬영·YOLO·VLM은 다시 실행하지 않는다. 추천을 받기 전이나 추천 밖 메뉴도 같은 방식으로 저장한다. 추천 목록으로 선택 가능 메뉴를 제한하지 않는다.
- `IDLE`에서 마이크를 연속으로 확인한다. 음성 활동 감지(VAD)로 말의 시작을 찾으면 `RECORDING`으로 넘어가고, 말이 끝나면 해당 발화만 STT로 전달한다. 키·버튼이나 고정 5초 녹음을 기본 입력으로 사용하지 않는다. 추천 이벤트는 STT 후의 질문 의도에 따라 시작한다.
- 메뉴 추천·재료 조회·메뉴 선택 어디에도 해당하지 않는 입력은 촬영·추천·기록 갱신을 하지 않고 안내 후 `IDLE`로 돌아간다.
- 작업 중 들어온 새 요청은 큐에 쌓지 않고 `BUSY`로 거절하는 초안이다. 무한 대기열을 만들지 않는다.
- 처리·TTS 재생 중 들어온 음성은 새 작업으로 넘기거나 대기열에 쌓지 않는다. 재생이 끝나면 남은 입력 버퍼를 비우고 연속 감지를 재개해 자기 응답을 새 질문으로 처리하지 않게 한다. 에코·잔향은 실제 장치에서 확인한다.
- 실패·취소는 해당 요청을 끝내고 `IDLE`로 돌아간다. 이전 성공 결과를 이번 결과로 내보내지 않는다.

## 4. YOLO와 VLM 연결

YOLO는 이름·상자·confidence를 반환하고, 코드는 후보를 나눈다. 두 기준값은 실제 사진을 보고 정한다.

| confidence | 처리 |
| --- | --- |
| `ACCEPT_CONF` 이상 | VLM 확인 없이 재료 목록에 추가 |
| `DETECT_CONF` 이상, `ACCEPT_CONF` 미만 | VLM 확인 후보 |
| `DETECT_CONF` 미만 | 탐지 후보에서 제외 |

- YOLO 실행의 `conf`에는 탐지 하한을 적용한다. 하한을 처음부터 너무 높여 애매한 후보가 모두 사라지지 않게 한다.
- 애매한 상자 영역을 같은 원본 사진에서 자르고, 후보 번호와 함께 한 이미지로 모아 `runtime/vlm_candidates.jpg`에 덮어쓴다. 해당 이미지와 후보 목록을 한 번만 VLM에 전달한다. 객체마다 별도 호출하지 않는다.
- VLM은 각 후보의 재료 ID 또는 확인 불가를 반환한다. 다른 지원 재료로 정정할 수 있지만 입력에 없던 후보·재료를 추가할 수는 없다.
- 확인 불가·잘못된 응답·호출 실패 때는 애매한 후보를 제외한다. 이미 확실한 재료는 유지하고, 보완 이미지 호출을 반복하지 않는다.
- 최종 목록은 YOLO의 확실한 재료와 VLM이 확인한 재료를 합쳐 종류별 중복을 제거한다. 모두 비면 재료 인식 불가로 안내한다.
- VLM 연동 검증에서는 실제 후보 이미지가 전달돼야 한다. 상자 좌표나 JSON만 읽게 한 실행은 이미지 분석 검증이 아니다.
- YOLO 점수와 VLM 판단을 하나의 확률로 합치거나, VLM이 확인했다는 이유로 confidence를 1로 바꾸지 않는다.
- YOLO 미검출 재료, 양·무게·가려진 재고·신선도를 이 과정으로 확정하지 않는다.

## 5. 메뉴 생성과 최종 검증

1. Gemma에 관측 재료, 명시적으로 허용한 상시 재료, 최근 음식의 정규화 이름·별칭을 전달한다.
2. 보유 재료를 활용하는 메뉴를 레시피 없이 JSON으로 최대 2개 생성하도록 요청한다. 여러 재료의 조합과 추가 구매가 필요한 메뉴를 허용하며 보유 재료와 구매할 재료를 분리한다.
3. 코드가 자료형, 허용 키, 비어 있지 않은 메뉴명, 중복, 최근 식사, 실제 보유 재료 ID, 추가 재료 목록을 검사한다. 관측하지 않은 재료를 보유 재료로 적으면 거절하되, 추가 구매 재료라고 명시했다면 허용한다.
4. 유효한 항목은 보존하고 잘못된 항목은 제외한다. 1~2개면 그대로 출력한다. 1개를 2개로 채우기 위한 추가 호출은 하지 않는다.
5. 올바른 응답에 유효한 후보가 없으면 `추천할 메뉴가 없어요`라고 안내한다. 잘못된 형식·금지 메뉴만 있는 결과는 최대 1회 수정 요청한다. 후보 없음과 형식 실패는 구분하고 무한 재생성하지 않는다.
6. 최종 출력은 코드의 템플릿으로 만든다. 1개면 `추천 메뉴는 A입니다.`, 2개면 `추천 메뉴는 A, B입니다.`에 필요한 추가 재료만 짧게 덧붙인다. 모델이 레시피·설명·지시문을 추가해도 그대로 TTS에 넘기지 않는다.

추가 구매 재료는 이름만 제안하고 매장 재고나 가격을 확인하지 않는다. 상시 재료는 명시적 설정만 인정한다. 구매 종류 수의 상한은 아직 미확정이며 메뉴당 최대 2종을 초안으로 제안한다.

`그래, 달걀말이 먹자`처럼 먹기로 한 메뉴를 명확히 말하면 파일에 저장하고 `달걀말이로 기록했어요.`라고 안내한다. 실제로 먹었음을 확인한 것이 아니라 먹기로 결정한 기록이다. 저장 실패 때는 성공 안내를 하지 않고 기존 파일을 보존하고 사용자가 다시 저장을 시도할 수 있게 한다.

`둘 다 먹자`라는 선택은 현재 이벤트에서 마지막으로 안내한 메뉴 모두로 해석해 함께 저장한다. 1개만 안내했다면 1개만 저장한다. 이 문맥은 추천 밖 메뉴를 제한하는 데 사용하지 않는다. 무엇을 먹기로 했는지 알 수 없으면 `그래서 뭘 드시나요? 알려주세요!`라고 묻고 저장을 보류한다.

## 6. 한 추천 이벤트와 다른 메뉴 요청

- 첫 메뉴 추천부터 이어지는 `딴 메뉴 없어?`, `다른 거 추천해 줘`를 하나의 추천 이벤트로 본다. 음성 한 문장마다 이벤트를 끝내지는 않는다.
- 처리 상태의 `IDLE`은 다음 입력을 기다린다는 뜻이며 추천 이벤트가 끝났다는 뜻은 아니다. 추천을 읽은 뒤에도 아래 종료 조건이 생기기 전까지 임시 목록을 유지한다.
- 현재 이벤트의 재료 목록, 마지막으로 안내한 메뉴 1~2개, 그동안 실제로 안내한 메뉴 이름 집합만 메모리에 둔다. 파일·질문별 폴더·관리 ID는 추가하지 않는다.
- 다른 메뉴 요청은 같은 재료 목록과 최근 3일 기록을 사용하고, 현재 이벤트에서 이미 안내한 모든 메뉴를 추가로 제외한다. 촬영·YOLO·VLM은 다시 실행하지 않고 메뉴 생성만 수행한다.
- 새 대안도 최대 2개이며 1개면 그대로 안내한다. 유효한 대안이 없으면 `추천할 메뉴가 없어요`라고 말하고 이벤트를 끝낸다. 세상의 모든 가능한 요리가 없다고 검증한 뜻은 아니다.
- 먹기로 한 메뉴의 저장 성공, 명시적 종료·취소, 후보 없음, 새로 시작하는 일반 추천, 프로그램 종료·재시작 때 임시 목록을 비운다. 저장 실패나 불명확한 선택으로 되묻는 중에는 이벤트를 유지한다.
- 이벤트 밖에서 `딴 메뉴 없어?`라고 하면 새 일반 추천처럼 현재 사진부터 분석한다. 새 이벤트에는 지난 이벤트의 단순 추천 이력을 적용하지 않는다.
- 재료 조회는 별도 응답이며 진행 중인 추천 문맥을 바꾸지 않는다. 재료가 바뀐 상태로 추천받으려면 새 일반 추천을 시작해 새 사진을 분석한다.

## 7. 가상환경과 장치

강의 노트북에서 확인한 시작 후보이며 실제 장치 연결 전 경로·패키지·장치 번호를 재확인한다.

| 기능 | Jetson의 시작 후보 |
| --- | --- |
| YOLO | `~/vision-llm/.venv/bin/python`, Project02 루트의 `ingredients_int8.engine` |
| Gemma VLM | `llama_cpp`, `Gemma4ChatHandler`, Gemma GGUF와 해당 mmproj 파일. 현재 환경에서 실제 호출 가능한지 확인 필요 |
| STT | `~/vision-llm/whisper.cpp/build-cpu/bin/whisper-cli`, `ggml-base.bin` |
| TTS | `~/vision-llm/.piper_venv/bin/python -m piper`, `ko_KR-kss-medium.onnx` |
| 녹음·재생 | `arecord`, `aplay`. 노트북의 `plughw:3,0`은 고정 요구사항이 아닌 장치 후보 |

실행 파일·모델·입출력 경로는 설정으로 정한다. `subprocess`에는 인수 목록을 전달한다. 사진·음성은 `runtime/camera.jpg`, `runtime/input.wav`, `runtime/response.wav`를 다음 질문 때 덮어쓰며, 질문별 폴더나 이력을 만들지 않는다. 다른 가상환경의 패키지를 메인 커널에서 직접 import할 필요는 없다.

Mac의 `.venv-ingredients`와 루트 `train_yolo_ingredients.py`는 학습용이다. Mac에서 얻은 `best.pt`를 Jetson으로 옮겨 실제 Jetson에서 식재료 사진으로 calibration하고 TensorRT INT8로 변환한다. 사용자 결정에 따라 FP32·FP16 엔진 생성은 필수 단계에서 제외한다. 양자화 전후 정확도는 `.pt`와 INT8 엔진으로 비교한다.

완성된 엔진을 `[Project02]/ingredients_int8.engine`에 둔다고 가정한다. 진입점 `main.py`의 위치로 Project02 루트를 계산하고 `PROJECT_ROOT / "ingredients_int8.engine"`을 어댑터에 전달한다. 엔진 파일의 실제 복사·검증이 완료됐다는 뜻은 아니며, 측정용 raw 엔진과 구별한다.

여러 프로세스도 Jetson 메모리를 공유한다. GPU 추론은 우선 순차 실행하며 모델 상주·재로딩 방식은 메모리·지연 측정 후 정한다. 학습·변환 작업은 이 구조 설계와 별개다.

## 8. 제안 파일 구조

다음은 앞으로 구현할 구조이며 아직 이 파일들이 존재한다는 뜻이 아니다.

```text
[Project02]/
  ingredients_int8.engine # 최종 INT8 모델 배치 가정; 아직 복사하지 않음
  recent_meals.json       # 최근 3일 식사 결정 기록; 구현 후 생성·갱신, 비공개
  main.py                 # 실행 진입점과 조정기 연결
  contracts.py            # 요청·관측·추천 데이터 타입
  policy.py               # 이름 정규화, 의도·출력 검증, 문장 생성
  history.py              # 날짜로 최근 기록 읽기, 메뉴 선택 시 저장
  pipeline.py             # 상태 전이와 단계 연결
  adapters/               # camera, yolo, gemma, stt, tts
  tests/                  # 장치 없는 하네스, 가상 입력, 기대 결과
  config/                 # 환경별 경로, 클래스 매핑, 음식 별칭
  runtime/                # 덮어쓰는 현재 사진·음성 파일; 버전 관리 제외
  documents/              # 설계와 실제 검증 기록
```
